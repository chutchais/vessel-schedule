8. Run `npm run db:migrate:status` again and retain redacted job metadata. Never retain connection strings.
9. Deploy/start the exact reviewed application artifact, initially with planner sharing disabled.
10. Complete health/auth/tenant smoke tests, then enable planner sharing only if its separate gates pass.

## 5. Backup and rollback

### Before release

- [ ] Confirm Supabase automated backup/PITR capability, schedule, retention, region, encryption, and restore permissions for the selected plan. No provider evidence is present in the repository.
- [ ] Create an approved pre-migration restore point/snapshot and record only its non-secret identifier and timestamp in the release record.
- [ ] Restore the backup into an isolated non-production project and verify authentication-related user mapping, organizations, audit records, planner data, and migration history.
- [ ] Name the incident commander, database operator, rollback decision deadline, recovery time objective, and recovery point objective.

### Rollback procedure

Prisma migrations do not provide automatic down migrations. Do not manually edit `_prisma_migrations` or run a destructive reset.

1. Stop traffic or switch to maintenance mode and disable public sharing.
2. If the schema is backward compatible, roll the application back to the prior immutable artifact while preserving the migrated database.
3. If data/schema integrity is affected, stop all writers and restore the approved pre-migration backup/PITR point into a new database/project according to the provider runbook.
4. Validate migration history, row counts, tenant isolation, auth identity mapping, audit continuity, and core planner reads before switching connection secrets/DNS.
5. Rotate any credentials exposed during the incident and document the recovery. Prefer a reviewed forward-fix migration when it is safer than restoring and losing post-snapshot writes.

**Blocker:** no repository evidence defines or proves a production backup policy, RPO/RTO, or successful restore rehearsal.
